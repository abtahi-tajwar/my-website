Fleeting Jobs Backend

Fleeting Jobs is a distributed job aggregation platform designed to automate the collection of job postings from modern company career portals. Rather than performing long-running browser automation inside the web application, the system delegates scraping to asynchronous Python workers while Spring Boot orchestrates persistence, messaging, and API access. RabbitMQ acts as the communication backbone, enabling loose coupling between services and significantly reducing API response times.

Spring Boot RabbitMQ PostgreSQL FastAPI Playwright BeautifulSoup Docker Distributed Systems

Overview

Modern career websites are increasingly built with JavaScript and often require full browser automation to extract structured job information reliably. Fleeting Jobs separates orchestration from execution by allowing Spring Boot to coordinate asynchronous Python workers responsible for Playwright-based scraping. Job data is streamed back through RabbitMQ, where Spring persists listings into PostgreSQL without blocking incoming HTTP requests.

Backend Components

Spring Boot
Provides REST APIs, coordinates scraping requests, consumes RabbitMQ events, performs persistence and exposes search endpoints.
FastAPI Worker
Executes asynchronous scraping tasks, launches Playwright browsers, parses HTML using BeautifulSoup, and publishes discovered jobs.
RabbitMQ
Decouples Spring Boot from the scraping worker, enabling asynchronous communication and independent scaling.
PostgreSQL
Stores companies, job listings, descriptions, metadata and future scraper configuration.

RabbitMQ Event Pipeline

Instead of returning a complete list of jobs over HTTP, the worker publishes each discovered job as an individual event. Spring Boot consumes these events and persists them immediately.

Why this approach?

Publishing individual events reduces coupling between services. Spring Boot no longer waits for the scraper to finish, allowing HTTP requests to return almost immediately while persistence continues asynchronously.

Engineering Decisions

Every major technology choice was driven by a specific engineering problem rather than simply adding another framework.

Spring Boot
Provides a mature ecosystem for REST APIs, dependency injection, persistence and messaging.
Python Worker
Playwright's Python ecosystem provides excellent support for modern JavaScript-heavy websites.
RabbitMQ
Decouples backend services and allows long-running scraping to continue independently of client requests.
PostgreSQL
Stores normalized company, job and description data while supporting future search capabilities.
AsyncIO
Allows concurrent browser automation and messaging without blocking the worker.

Implementation Highlights

  • Designed asynchronous Playwright workers capable of scraping modern JavaScript-rendered career portals.
  • Implemented RabbitMQ publishers and consumers for event-driven communication between Python and Spring.
  • Built background processing so HTTP requests return immediately while scraping continues independently.
  • Persisted job listings and descriptions separately, allowing incremental enrichment as scraping progresses.
  • Implemented pagination support for companies with hundreds of job postings.

Technical Challenges

Blocking Requests
Originally every API call waited for browser automation to finish.

Solution: Background workers with asynchronous messaging.
Java ↔ Python
The backend required reliable communication between two different runtimes.

Solution: RabbitMQ message queues.
Dynamic Websites
Traditional HTTP scraping could not execute JavaScript.

Solution: Playwright browser automation.
Incremental Updates
Job descriptions became available after the listing itself.

Solution: Publish additional events to enrich existing records.

Lessons Learned

  • Long-running browser automation should never block HTTP requests.
  • Message queues simplify communication between heterogeneous services.
  • Separating orchestration from execution produces a cleaner architecture.
  • Asynchronous processing dramatically improves user experience without increasing complexity for API consumers.
  • Designing around events rather than direct service calls makes future scaling significantly easier.
